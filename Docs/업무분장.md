## 1. 왜 필요한가

같은 사실을 두 곳에 두면 반드시 어긋납니다. 이미 두 번 겪었습니다.

| 사례 | 결과 |
|---|---|
| 기구 링크 길이가 코드와 실물에서 달랐음 (work11 §6.25) | 역기구학이 계산한 발끝 위치 자체가 틀려, 그 위에서 찾은 보행 파라미터가 전부 오차를 우회하는 보정이었음 |
| 서보 오프셋이 두 곳에 존재 | 8/19 재캘리브레이션이 한쪽에만 반영되어, COO 는 `[179, 88, 81, 13, ...]`, CTO 는 `[165, 83, 79, 25, ...]` 로 어긋난 상태였음 |
| `standingTrunkHeight` 를 COO 가 자체 계산 | COO 는 0.120 m, 실제는 **0.262 m**. 보상의 base_height 목표가 2배 넘게 틀렸음 |

**원인은 참조할 단일 출처가 없었던 것입니다** (CTO 정정). 8/19 시점에 오프셋은
`JetsonNano/servo_controller.py` 안에 리터럴로 있었고, 그 파일은 `adafruit`·`board` 를
import 해 로봇 밖에서는 열 수조차 없었습니다. `Common/servo_map.py` 는 8/20 에
만들어졌습니다.

> 같은 문제가 한 군데 더 있었습니다. `JetsonNano/examples/servo_check.py` 가
> `servo_controller.py` 의 **소스를 정규식으로 파싱**해 오프셋을 읽고 있었고,
> import 로 바꾸자 매칭이 깨져 조용히 `[90]*12` 로 폴백했습니다. 실기에서 서보를
> 엉뚱한 곳으로 보낼 수 있었습니다.

**그래서 경계를 "누가 무엇을 만드는가"가 아니라 "어떤 사실을 누가 소유하는가"로 정합니다.**

## 3. 경계선 — `rl/` 를 파일 단위로 나눔

```
rl/
├── gen_mjcf.py        A   실측 상수 -> MJCF 생성
├── validate_mjcf.py   A   순기구학 대조 등 검증 게이트
├── fk_mapping.py      A   관절 인덱스 매핑
├── mjcf/              A   생성 산출물          (COO 는 읽기 전용)
│   ├── spotmicro.xml
│   └── scene_flat.xml
│
├── envs/              B   Gymnasium 환경, 관측·행동·보상
├── train.py           B   PPO 학습
├── eval.py            B   정책 평가
└── runs/              B   학습 산출물 (git 제외)
```

**상대 영역의 파일은 직접 고치지 않고 요청합니다.**

## 4. 인터페이스 — COO 가 지킬 규칙

COO 는 아래에서 **읽기만** 하고 값을 **복제하지 않습니다.**

**`rl/model_api.py` 하나만 보면 됩니다.** CTO 가 학습에 필요한 형태로 가공해 두었습니다.

```python
from rl.model_api import (
    MJCF_SCENE, MJCF_ROBOT,   # 경로 — 직접 문자열로 적지 말 것
    JOINT_ORDER,              # (12,) 관측·행동 벡터의 관절 순서
    standingQpos,             # 기립 자세 = 정책의 default_joint_pos
    standingTrunkHeight,      # 보상 base_height 목표 (0.262 m)
    jointRanges,              # (12,2) 실측 서보 영점에서 유도된 가동 범위
    jointSigns,               # MJCF <-> kinematics 부호
    qposToServo,              # 정책 출력 -> 서보 각도 (실물 배포 경로)
)
```

**주의 — 관절 순서가 두 가지입니다.** `JOINT_ORDER` 는 다리마다 `(shoulder, leg, foot)`,
서보 인덱스는 `(Lower, Upper, Shoulder)` 로 **역순**입니다. `qposToServo()` 가 재정렬을
안에서 처리하므로 **직접 변환하지 마십시오.**

**금지**
- 기구 치수·서보 오프셋·관절 이름·가동 범위를 COO 의 파일에 하드코딩
- `rl/mjcf/*.xml` 직접 편집 — 모델 변경은 CTO 에게 요청해 `gen_mjcf.py` 를 고침

**COO 가 소유하는 값** (실물에 대응물이 없는, 학습 전용 값)
```
보상 가중치 · TRACKING_SIGMA · 관측 구성 · ACTION_SCALE
속도 명령 범위 · 도메인 랜덤화 폭 · PPO 하이퍼파라미터 · 종료 조건
```

## 5. 서로에게 넘기는 것

### CTO → COO

| 항목 | 형태 |
|---|---|
| MJCF 갱신 | `validate_mjcf.py` **전 항목 통과 후** 통보, 무엇이 바뀌었는지 한 줄 |
| 실측값 갱신 (치수·질량·오프셋) | 해당 모듈 커밋 + 통보 |
| **실물 보행 정량값** | 전진 속도(m/s), 1m 주행 시간, 연속 보행 거리 — 보고서 빈칸 |
| **하드웨어 사실관계** | 서보 모델, 보드 사양, 전원 구성 — 보고서 개발환경 |

### COO → CTO

| 항목 | 형태 |
|---|---|
| 학습 결과 | 전진 속도, 생존 시간, 보상 곡선 |
| 모델 수정 요청 | 관절 범위, 마찰, 액추에이터 파라미터 — 이유와 함께 |
| 실물 검증 요청 | 정책 이식 전 서보 매핑 확인 등 |
| 저장소 규칙 | 브랜치·커밋·PR 방식, 커밋하면 안 되는 것 |

## 6. 충돌 규칙

1. **사실은 소유자를 따른다.** 기구·하드웨어 수치는 CTO 가 정본, 학습·보상·평가 설정은 COO 가 정본.
2. **보고서는 COO 가 쓰고 CTO 가 검증한다.** CTO 는 하드웨어·기구 사실관계 오류를 근거(일지 절 번호)와 함께 지적하고, 문장 반영은 COO 가 한다.
3. **같은 파일을 동시에 고치지 않는다.** 필요하면 먼저 알린다.
4. **경계가 애매하면 이 문서를 먼저 고치고 작업한다.**
