# SpotMicro Week 14 — RC 전자 스위치 출력전압 테스트 + v10 전원/센서 설계 메모

> 작성일: 2026-09-27

---

## 1. 목적

모터 전원 차단용 RC 전자 스위치(PWM 신호로 온/오프하는 저가 모듈) 2개를 쓸
예정인데, 이 신호가 실제로 출력 전압을 제대로 스위칭하는지 확인하는 테스트
코드가 필요하다. 이 모듈은 ON/OFF가 갈리는 정확한 펄스폭이 데이터시트에
없어서 실측으로 찾아야 한다.

## 2. 현재 배선 상태 (실측)

| 스위치 핀 | 연결 | RPi 물리핀 | 비고 |
|---|---|---|---|
| + (VCC) | 3.3V | 17 | |
| - (GND) | GND | 14 | |
| S (신호) | GPIO18 (PWM0) | 12 | 하드웨어 PWM 채널 |
| 전원 입력(스위칭 경로) | 벤치 9V 공급 | - | 지금은 로봇 배터리(11.1V) 대신 9V로 단독 테스트 중 |

실제 로봇에서는 이 스위치를 XL4015 두 개 입력단(SW1 출력 11.1V 버스)에
하나씩 넣고, S는 GPIO18에서 Y분기해서 둘 다 동시에 같은 신호로 제어한다
(독립 제어는 필요 없다고 판단함 — 5.2절 참조).

## 3. 테스트 코드 요구사항

- GPIO18에 50Hz PWM을 생성하고, 펄스폭을 1000~2000us 범위에서 스텝으로
  바꿔가면서 사용자가 멀티미터로 스위치 출력단(현재는 9V 벤치 공급 쪽 출력)을
  직접 찍어 확인할 수 있게 한다.
- 각 스텝마다 현재 펄스폭 값을 콘솔에 출력해서, 어느 값에서 on/off가
  갈리는지 사용자가 기록할 수 있게 한다.
- (선택) 3.3V 로직레벨이 이 모듈에서 확실히 HIGH로 인식되는지도 이 테스트로
  같이 확인한다.

## 4. 중요 — 이 저장소의 GPIO 관례와 상충하는 지점

`Common/servo_oe.py`를 보면 이 프로젝트는 **root 권한 없이 돌아가야 한다는
이유로 RPi.GPIO/digitalio(Blinka) 대신 gpiod(문자 장치, `/dev/gpiochipN`)를
쓴다.** gpiod는 단순 디지털 온오프엔 충분하지만, 50Hz/1~2ms 펄스폭 같은
정밀 타이밍 PWM을 순수 파이썬 sleep 루프로 gpiod 위에서 만들면 지터가 심해서
믿을 수 없다.

이 테스트는 실제 서보급 타이밍 정밀도가 필요하니, 코딩 세션에서 다음 중
하나를 골라야 한다:

- **하드웨어 PWM sysfs (`/sys/class/pwm/pwmchip0/...`)**: 커널이 직접
  타이밍을 잡아서 지터가 없다. udev 규칙으로 non-root 접근을 만들 수 있어서
  이 저장소의 "root 회피" 방향과 맞는다.
- **pigpio 데몬**: 데몬 자체는 보통 sudo로 한 번 띄워두고, 클라이언트는
  non-root로 소켓 통신한다. 별도 서비스 의존성이 새로 추가된다.

어느 쪽으로 정하든, `servo_oe.py`처럼 이유를 주석으로 남겨두는 게 나을 것
같다.

## 5. 오늘 논의에서 나온 추가 배경 (v10 전원/센서 설계)

### 5.1 모터 전원 차단 설계

- SW2(기존 긴급정지, 모터만 차단하는 물리 스위치)는 그대로 유지한다. RC
  전자스위치는 SW2를 **대체하는 게 아니라 SW2 뒤에 추가되는 소프트웨어 제어용
  보조 차단**이다.
- 이유: 라즈베리파이/PCA9685가 멈추면 소프트웨어 차단은 못 미덥다. 진짜
  안전장치는 물리 스위치여야 한다.
- **제어 코드를 짤 때도 이 원칙을 지켜야 한다** — RC 스위치 제어 로직이
  유일한 안전장치인 것처럼 다루면 안 된다.

### 5.2 RC 전자스위치 스펙 관련 주의

- 제품은 20A 정격 표기인데 실제 달려있는 와이어는 22AWG(실사용 한계
  5~7A)라서, XL4015 두 개 입력단에 하나씩(각각 대략 5A) 나눠서 써서 여유를
  만들었다.
- **+(VCC)는 PCA9685의 V+(서보 패스스루, XL4015 출력)에 물리면 안 된다** —
  스위치 OFF -> XL4015 출력 죽음 -> 스위치 제어전원도 같이 죽어서 다시 못
  켜지는 데드락이 생긴다. 그래서 PCA9685를 거치지 않고 RPi GPIO에서 직접
  PWM을 생성하는 쪽으로 결정했다 (지금 이 테스트가 그 첫 단계).
- 전원측 입/출력 GND, PWM측 GND가 전부 같은 노드인 걸 멀티미터로 확인함
  (하이사이드만 스위칭하는 구조) — 그래서 GND는 아무 핀이나 공통버스에
  물리면 된다.

### 5.3 공통 GND/전원 버스

- 배터리(-)/SMPS(-)/XL4015 x2/UBEC GND는 전부 공통 노드다. XL4015, UBEC
  둘 다 비절연 벅컨버터라 입출력 GND가 내부에서 이미 short돼 있다 (필요하면
  도통테스트로 재확인).
- 물리적으로는 GND용, SW1 출력(11.1V)용을 각각 소형 스크류터미널블록(15A급,
  4극)으로 분배할 예정 — 이건 조립 파트라 코드와는 무관.

### 5.4 BNO085 IMU

| 핀 | RPi 물리핀 |
|---|---|
| VIN | 3.3V (1 또는 17) |
| GND | 아무 GND |
| SDA | GPIO2 (3) |
| SCL | GPIO3 (5) |
| RST | GPIO17 (11) - 2026-09-29 추가, 스톨 자동 복구용. 아래 5.4.2 참고 |

- I2C 주소는 실측 0x4B (`i2cdetect -y 1`, 2026-09-28/29). 이 문서 작성
  시점 예상은 0x4A였는데 실측이 다르다. PCA9685의 0x40/0x41과는 겹치지
  않는다.
- 부착 방향: 센서 Y축 = 로봇 전방, 센서 X축 = 로봇 좌측, 센서 Z축 = 로봇
  하방. 미러링이 아니라 정상 우수좌표계 회전이라 소프트웨어 축 리매핑으로
  처리할 수 있다:
  - `robot_forward = sensor_Y`
  - `robot_left = sensor_X` (`robot_right = -sensor_X`)
  - `robot_down = sensor_Z` (`robot_up = -sensor_Z`)
- 조립 후 로봇을 실제로 기울여보고 출력이 예상 방향과 맞는지 검증 필요
  (조립 실수로 진짜 미러링됐을 가능성 배제 못 함).
- 진단 스크립트: `RaspberryPi/examples/test_bno085.py`.

#### 5.4.1 I2C 클럭 스트레칭 문제 (2026-09-28/29 실측)

BNO085를 I2C로 붙이자 `adafruit_bno08x` 라이브러리가 몇 초~몇 분 안에
죽거나 멈추는 문제가 나왔다. 근본 원인은 RPi 하드웨어 I2C 컨트롤러
(BCM283x/2711)가 BNO085 의 clock stretching 을 스펙대로 못 받아주는
알려진 이슈다(`adafruit/Adafruit_CircuitPython_BNO08x#9`). "RPi + I2C
IMU 자체가 불가능하다"는 뜻은 아니다 - 실제로 흔한 조합이고, 문제는
간헐적으로 패킷이 깨질 때 `adafruit_bno08x` 가 그걸 못 버티고 그냥
죽어버리는 것이다. 클럭을 10kHz 까지 낮춰봤지만 오히려 리포트 자체가
안 오는 더 나쁜 상태가 됐다 - 기본 100kHz 로 되돌리고 아래처럼
소프트웨어 쪽에서 각 실패 양상을 흡수하는 방향으로 갔다.

실측한 실패 양상 네 가지, `test_bno085.py` 에 대응책까지 구현:

1. **패킷 파싱 실패** - report_id 를 모르는 패킷을 받으면 라이브러리가
   `KeyError` 로 죽는다. `BNO08X._handle_packet` 을 몽키패치해서 그
   패킷만 버리고 계속 진행하게 함. 실측 손상율 5~9%.
2. **버스 트랜잭션 자체 실패** - 헤더 4바이트를 읽는 시점에
   `OSError: [Errno 5] Input/output error`. 메인 루프에서 이 사이클만
   버리고 재시도. 실측 실패율 ~1%.
3. **payload 오염** - report_id 는 정상이라 파싱은 성공하는데 값 자체가
   물리적으로 불가능(로봇이 정지 상태인데 accel 이 127 m/s² 로 튐, 정확히
   같은 값이 재현됨 - 랜덤 노이즈가 아니라 재현 가능한 손상 패턴).
   가속도 40 m/s² 초과, 자이로 35 rad/s 초과(센서 풀스케일 근처), 쿼터니언
   norm 이 1 에서 0.3 이상 벗어나면 버리는 sanity filter 로 대응.
4. **스톨** - 통신(헤더 읽기)은 계속 성공하는데 BNO085 가 "새 리포트
   있음" 신호를 영영 안 주는 상태. 한 번 걸리면 소프트웨어 재시도로는
   절대 못 푼다 - 크래시도 안 하고 실패로도 안 잡히는데 실제로는 죽은
   캐시값만 계속 나온다. 이게 가장 심각했다 (5.4.2 참고).

#### 5.4.2 스톨 자동 복구 - RST 핀 필요

스톨은 소프트웨어 재시도로 못 풀리므로 센서를 물리적으로 재부팅해야
한다. `adafruit_bno08x` 의 `hard_reset()` 은 RST 핀을 HIGH->LOW->HIGH 로
토글하는데(10ms 펄스), 이건 I2C 버스 상태와 완전히 독립적인 GPIO 신호라
버스가 막혀있어도 무조건 작동한다. 처음엔 RST 를 안 썼는데(`reset=None`)
이 경우 `hard_reset()` 이 그냥 아무것도 안 하고 리턴하는 죽은 코드였다.

RST 를 GPIO17(물리핀 11)에 연결하고 스톨 감지(2초 이상 새 패킷 없음)
시 자동으로 `bno.initialize()`(hard_reset -> soft_reset -> ID 확인) 를
호출하도록 구현. 실측 결과 **11회 스톨 발생, 11회 전부 자동 복구
성공** - 장시간 무인 실행이 가능해졌다.

두 가지 추가로 걸린 문제:

- **digitalio 대신 gpiod** - `digitalio.DigitalInOut(board.D17)` 은
  `/dev/mem` 을 직접 열어 root 를 요구한다(`RuntimeError: No access to
  /dev/mem`). `Common/servo_oe.py` 가 같은 이유로 gpiod 를 썼던 것과
  동일한 문제라, `test_bno085.py` 에도 `_GpiodResetPin` 이라는 얇은
  래퍼(`.direction =`, `.value =` 대입만 gpiod 위에 얹음)를 만들어 gpiod
  로 RST 를 잡는다.
- **리셋 직후 정착 시간 부족** - `initialize()` 내부에서 `hard_reset()`
  직후 곧바로 `soft_reset()`(I2C 쓰기) 을 시도하는데, 라이브러리 기본
  대기(10ms)로는 이 환경에서 부족해서 `soft_reset()` 이 `OSError` 로
  실패했다. `hard_reset()` 을 몽키패치해서 토글 후 0.5초를 더 기다리게
  하고, 연결/재초기화 양쪽에 재시도 루프(최대 3회)를 추가해서 해결.

#### 5.4.3 GPIO17 핀 충돌 -> OE 안전 기능 제거 (2026-09-29)

RST 를 GPIO17 에 연결하고 재부팅했더니 `gpiod.request_lines()` 가
`OSError: [Errno 16] Device or resource busy` 로 실패했다. 원인은
`Common/servo_oe.py` 가 PCA9685 OE(Output Enable) 핀으로 **같은
GPIO17** 을 쓰고 있었고, 재부팅으로 `spotmicro-gait.service` 가 자동
시작되면서 그 핀을 상시 점유하고 있었기 때문. 재부팅 전 테스트들에서
문제가 없었던 건 그 세션들에서 gait 서비스가 안 돌고 있었을 뿐이다.

임시로 RST 를 GPIO27(물리핀 13)로 옮겨서 우회했으나, OE 기능(서보
릴리즈 페일세이프, work11.md §6.20) 자체를 더 이상 쓰지 않기로
결정하면서 최종적으로는 기능을 통째로 제거했다:

- `Common/servo_oe.py` 삭제
- `RaspberryPi/servo_controller.py` - `OutputEnable`/`configurePCA`
  사용 제거. `releaseAll()` 은 이제 PWM 만 끊고(서보는 마지막 목표값을
  계속 물고 있다), OE 로 신호선을 놓는 실제 릴리즈는 더 이상 없다.
- `RaspberryPi/examples/servo_check.py` - 같은 이유로 OE 관련 코드와
  `holdUntilEnter()`(OE 페일세이프 배선에서 프로세스 종료 시 자동
  릴리즈되는 걸 막으려고 Enter 대기하던 함수, OE 가 없으면 존재 이유가
  없다) 제거.
- RST 는 GPIO17(물리핀 11)로 최종 확정.

#### 5.4.4 최종 실측 (2026-09-29, GPIO17 확정 + OE 제거 후)

장시간(로그 1278줄) 무인 실행 결과:

| 지표 | 수치 |
|---|---|
| 패킷 손상율 | ~6% |
| 버스 I/O 실패율 | ~1% |
| 값 검증(sanity) 거부율 | ~11% |
| 스톨 발생 / 자동 복구 | 11회 / 11회 (100%) |
| 최종 유효 데이터 비율(추정) | ~88% |

GPIO17 로 되돌린 뒤에도 GPIO27 테스트 때와 손상율/거부율이 비슷해서,
RST 핀 번호 자체가 신호 품질에 영향을 준 건 아닌 것으로 보인다.

미검증 가설: 지금 쓰는 CM4 캐리어 보드(Waveshare CM4-to-Pi4-Adapter)의
I2C 풀업 저항이 스키매틱상 4.7kΩ 로, 공식 CM4(1.8kΩ)/CM4IO(2.2kΩ)보다
커서 clock stretching 상황의 타이밍 마진이 더 좁을 수 있다 - 웹 검색
결과에 기반한 추정이고 실측(오실로스코프 등)으로 확인하지는 않았다.
Y케이블(PCA9685+BNO085 동시 연결)과 BNO085 단일 점퍼 비교에서는 유의미한
차이가 없었다 - 자작 케이블의 납땜 품질이 주 원인은 아닌 것으로 보인다.

다음 과제(우선순위 미정): 외장 풀업 저항(2.2kΩ 정도 병렬 추가)으로
손상율을 더 낮출 수 있는지 검증, 또는 UART-RVC 모드 전환(배선 변경
필요, 쿼터니언 대신 오일러각만 나옴) 검토.
