### 2. `Kinematics.kinematics` / `Common.servo_map` import 가능 여부

| 모듈 | 판정 | 비고 |
|---|---|---|
| `Common.servo_map` | **안전** | import 문이 하나도 없는 순수 데이터. 순환 참조 없음 |
| `Kinematics.kinematics` | **문제가 있었고, 오늘 고쳤습니다** | 아래 |

`kinematics.py` 는 모듈 최상위에서 이런 일을 하고 있었습니다.

```python
import matplotlib.pyplot as plt
fig = plt.figure()            # import 만 해도 figure 를 만든다
data = np.random.rand(2, 25)  # 전역 난수 상태를 소비한다
```

세 가지가 B 에게 문제가 됩니다.
- matplotlib 이 없는 환경에서는 **import 자체가 실패**
- 학습 환경을 병렬로 띄우면 **프로세스마다 figure 생성** (헤드리스 백엔드 문제)
- `np.random.rand` 가 **전역 난수 상태를 소비해 시드 재현성을 깬다**

matplotlib 을 지연 로딩으로 바꿨습니다. 검증했습니다.

```
matplotlib 을 막은 상태에서:  import 성공, l3=125 l4=138 L=185 W=78
                              전역 난수 상태 보존: True
```

**결론: 둘 다 import 하십시오.** 하드웨어 의존은 딸려오지 않습니다.

### 3. `rl/mjcf/scene_flat.xml` 경로 안정성

### 4. `Common/servo_map.py` 공개 API 확정 여부

**확정입니다.** 실제 공개 심볼은 B 가 적은 4 개보다 하나 많습니다.

```python
SERVO_OFFSETS      # (12,)  서보 인덱스 순
SERVO_SIGN         # (12,)  (다리, theta 인덱스, 부호)
JOINT_NAMES        # (12,)  "FL-Lower" 등
FUTABA_INDICES     # {5}    FR-Shoulder 만 Futaba 25kg
SERVO_MIN, SERVO_MAX   # 0, 180  실물 클램프 범위
thetaLimitsDeg()   # 각 서보가 허용하는 theta 범위 (12, 2) 도
```

**다만 B 는 이것들을 직접 쓸 일이 거의 없습니다.** 학습에 필요한 형태로 가공해
`rl/model_api.py` 에 모아 두었습니다.

```python
from rl.model_api import (
    MJCF_SCENE, MJCF_ROBOT,   # 경로
    JOINT_ORDER,              # (12,) 관측·행동 벡터의 관절 순서
    standingQpos,             # 기립 자세 = 정책의 default_joint_pos
    standingTrunkHeight,      # 보상의 base_height 목표값 (0.262 m)
    jointRanges,              # (12,2) 가동 범위. 실측 서보 영점에서 유도됨
    jointSigns,               # MJCF <-> kinematics 부호
    qposToServo,              # 정책 출력 -> 서보 각도 (실물 배포 경로)
)
```

**주의 — 순서가 두 가지입니다.**
`JOINT_ORDER` 는 다리마다 `(shoulder, leg, foot)` 이고, 서보 인덱스는
`(Lower, Upper, Shoulder)` 로 **역순**입니다. `qposToServo()` 가 그 재정렬을
안에서 처리하므로 B 는 신경 쓸 필요가 없습니다. 직접 변환하지 마십시오 —
저도 이 모듈을 처음 쓸 때 이 순서를 틀렸습니다.

### 7. 액추에이터가 위치 제어인가

**위치 제어입니다.** 확인했습니다.

```xml
<position kp="25" kv="0.315" forcerange="-3.0 3.0"/>
```

`kv` 는 임의 값이 아니라 서보의 토크-속도 직선에서 유도했습니다 —
`kv = forcerange / 무부하각속도 = 3.0 / 9.51 rad/s = 0.315`. 이렇게 두면
액추에이터가 **실제 서보보다 빠르게 움직일 수 없습니다.** DS3235 무부하 정격
545°/s 가 그 근거입니다.

**단, `kp=25` 와 `armature=0.008` 은 아직 실측이 아닙니다.** 서보 스텝 응답을
찍어 동정해야 하고, 그때까지 도메인 랜덤화 폭을 넓게 (`kp` ±40%, `armature` ±50%)
두시길 권합니다.

인덱스 5 (FR-Shoulder) 만 Futaba 25kg 이라 `forcerange` 를 2.5 로 낮춰 두었습니다.

### 8. 기립 자세에서 관절 여유

계산했습니다. **여유가 넉넉해서 관절 한계 페널티는 우선순위가 낮습니다.**

| 관절 | 기립각(도) | 하한 | 상한 | 여유 |
|---|---:|---:|---:|---:|
| FL_shoulder | 0.0 | −79 | 101 | 79.0 |
| FL_leg | 36.2 | −83 | 97 | 60.8 |
| FL_foot | −56.9 | −165 | 15 | 71.9 |
| FR_leg | 36.2 | −97 | 83 | 46.9 |
| **RR_leg** | 36.2 | −99 | 81 | **44.8** ← 최소 |
| RR_foot | −56.9 | −157 | 23 | 79.8 |

*(전체 12개는 `python -m rl.model_api` 로 출력됩니다)*

몸통 높이를 조절 범위 전체로 훑어도 최소 여유가 유지됩니다.

| height | 60 | 80 | 100 | 110 | 120 | 130 |
|---|---:|---:|---:|---:|---:|---:|
| 최소 여유(도) | 23.8 | 31.5 | 40.0 | **44.8** | 50.4 | 49.4 |

**해석**: `ACTION_SCALE = 0.25 rad` (14.3°) 이면 최악의 관절(RR_leg)도 한계까지
**3회분 이상** 남습니다. 관절 한계는 구속 조건이 아닙니다. 페널티를 넣더라도 약하게
두고, 그 예산을 착지 충격·토크 포화 쪽에 쓰는 편이 낫습니다.

여유가 좌우 비대칭인 것(FL_leg 60.8 vs RR_leg 44.8)은 오차가 아니라 **혼이 스플라인에
물린 위치가 서보마다 다르기 때문**입니다 (work11 §6.6). 정상입니다.

### 보상 설계에 영향을 주는 발견

**기립 자세에서 무게중심이 대각 지지선과 11.4mm 어긋납니다.**

```
정지 무게중심  -25.2mm   (설계값, 앞발 하중 실측에서 유도)
기립 무게중심  -36.4mm   (다리가 뒤로 기울며 다리 질량 1.02kg 이 함께 이동)
대각 지지선    -25.0mm
```

트롯은 주기의 일부를 대각선 두 발로만 버티고 그때 지지면이 선이므로, 이 어긋남이
뒤로 주저앉는 경향으로 나타날 수 있습니다. 계측으로는 안 보이고 시뮬레이션에서
나온 값입니다.

**B 에게 주는 함의**: `base_height` 목표를 고정값으로 두면 정책이 이 편향을 몸통
자세로 상쇄하려 들 수 있습니다. `flat_orientation` 가중치와 함께 보시고, 학습된
정책의 정상 상태 pitch 가 0 이 아니라면 이것이 원인입니다.

### 도메인 랜덤화 — 실측 근거가 있는 값들

추측 대신 쓸 수 있는 숫자입니다.

| 파라미터 | 폭 | 근거 |
|---|---|---|
| **서보 영점 오차** | **±8°** | 각도 실측에서 FL +7, FR +7, RL +15, RR +2 (work11 §0). 혼 스플라인 한 칸이 14.4° 라 재체결하면 이만큼 튄다 |

| 링크별 질량 | ×[0.8, 1.2] | 총 2.2kg 만 실측, 배분은 추정 |
| 제어 지연 | 0~2 스텝 | 아직 미측정. 실측 전까지 넓게 |

서보 영점 오차가 가장 중요합니다. **혼이 한 칸 어긋난 로봇을 본 적 없는 정책은
실물에서 그걸 만나면 넘어집니다.** 우리는 그 값을 실제로 재 뒀습니다.

  배선은 미완)
