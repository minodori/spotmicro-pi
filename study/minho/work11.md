### 3.1 IO 보드 & 전원

- IO 보드: RPi 5와 동일한 외형·포트 구성의 서드파티 캐리어. **전원 입력은 USB-C 뿐** (12V 배럴잭 없음)
- 현재 급전: `LiPo 11.1V → UBEC 5V/5A → GPIO 헤더 4번 핀`

work08.md의 전원 아키텍처(UBEC 5V = 로직, 300W 벅 7.4V = 서보, GND 공통)는 **그대로 유효**하다.

**CM4가 RPi 5보다 유리한 점**: 소비전력이 낮고(대략 5W vs 8W), BCM2711은 RPi 5의 PMIC(DA9091)처럼 까다로운 300ms 내 4.75V 안정화를 요구하지 않는다. work08.md에서 겪은 부팅 실패 문제가 재발할 여지가 작다.

> **USB-C 급전 관련**: UBEC은 PD 컨트롤러가 없는 단순 레귤레이터라 전압 협상 자체가 일어나지 않는다. VBUS에 5V가 그대로 실릴 뿐이므로 "다른 전압으로 협상될" 위험은 없다. 다만 CC 저항 유무가 케이블/보드마다 달라 안 켜질 수 있어, 현재는 GPIO 5V 급전을 유지 중이다.
>
> GPIO 5V 핀은 보드의 입력 보호 회로를 우회하므로, 대신 **UBEC 출력에 인라인 퓨즈(3~5A)** 와 **CM4 근처 벌크 커패시터(470~1000µF)** 를 두는 편이 실질적인 보호가 된다.

### 3.2 비상 정지 설계

전체 전원을 끊으면 CM4가 강제 종료되어 eMMC 파일시스템 손상 위험이 있다. **E-stop은 서보 V+ 라인에만 거는 것이 옳다.**

```
LiPo 11.1V ─┬─ UBEC 5V ────────→ CM4              (항상 유지)
            └─ 300W Buck 7.4V ─→ [E-stop] → PCA9685 V+  (차단 대상)
```

구동계만 끊고 연산부는 살리는 것이 로봇공학의 표준 관행이다. 서보가 풀려도 로봇을 공중에 매달아 둔 상태면 안전하다.

## 4. CM4 전환 시 걸린 함정 4가지

RPi 5에서는 없던 문제들이라 별도로 기록한다.

### 4.1 Blinka가 `RPi.GPIO`를 추가로 요구

CM4는 BCM2711이라 Blinka가 `raspi_4b` 보드 모듈로 인식하고, 이 경로는 `RPi.GPIO`에 의존한다. RPi 5(BCM2712)에는 없던 의존성이다.

```
ModuleNotFoundError: No module named 'RPi'
RuntimeError: The platform library 'RPi' was not found.
```

```bash
pip install RPi.GPIO
```

설치 후 정상 인식:
```
chip: BCM2XXX
board: RASPBERRY_PI_CM4
SCL: 3    SDA: 2      ← work05.md 핀맵과 동일, 코드 수정 불필요
```

### 4.2 `i2c-tools` 설치가 udev 그룹을 덮어쓴다

Ubuntu 기본 규칙 `/lib/udev/rules.d/60-gpio.rules`는 `/dev/i2c-*` 를 `dialout` 그룹으로 두지만, `i2c-tools` 패키지가 설치하는 `60-i2c-tools.rules`가 파일명 순서상 나중에 적용되어 그룹을 `i2c`로 바꾼다.

```
설치 전: crw-rw---- root dialout /dev/i2c-1
설치 후: crw-rw---- root i2c     /dev/i2c-1
```

→ `dialout`만 추가하면 `Permission denied`. **두 그룹 모두 추가**해야 한다.

```bash
sudo usermod -aG dialout,i2c $USER
```

### 4.3 그룹 추가는 재로그인해야 적용된다

리눅스 그룹 멤버십은 로그인 시점에 고정된다. `usermod` 이전에 열어둔 SSH 세션에서는 계속 `Permission denied`가 난다.

```bash
exit && ssh ...        # 재로그인
# 또는
newgrp i2c             # 새 셸이 뜨므로 venv 재활성화 필요
```

### 4.4 `input()`에서 방향키가 안 먹는다

대화형 스크립트에서 오타 수정이 안 되고 `^[[D` 같은 이스케이프 시퀀스가 그대로 찍힌다. `readline` 모듈을 import하면 해결된다.

```python
import readline  # noqa: F401  input() 편집 기능 활성화
```

## 6. 서보 채널 실측 — 인덱스와 채널 번호 혼동

### 6.1 두 번호 체계

혼동이 실제 배선 오류로 이어졌으므로 명확히 구분해 둔다.

| 구분 | 범위 | 의미 |
|------|------|------|
| **서보 인덱스** | 0~11 | 12개 관절의 논리 번호. `_servo_offsets`, `_val_list`, IK 결과가 공유하는 순서 |
| **보드 채널** | CH0~CH5 | 각 PCA9685의 물리 헤더 번호. 보드가 2개라 각각 0부터 다시 셈 |

둘을 잇는 것이 `servo_controller.py`의 `_channel_map`이다.

```
인덱스 6 (RL-Lower) → 0x41 보드 CH3 → 좌측 보드 앞에서 4번째 헤더
```

**인덱스 6,7,8을 "앞에서 7,8,9번째 헤더"로 오해**해 RL 다리를 CH6~CH8에 연결했던 것이 이번 배선 오류의 원인이었다. 코드는 CH0~CH5만 사용하므로 해당 채널은 전혀 동작하지 않았다.

### 6.2 채널 스캔 결과 (재배선 전)

`servo_check.py scan`으로 12채널을 순차 구동해 실측했다.

| 보드/채널 | 실측 | 기대값 | 판정 |
|-----------|------|--------|------|
| 0x41 CH0~2 | fl-lower / fl-upper / fl-shoulder | FL 3개 | ✅ 일치 |
| 0x41 CH3~5 | — | RL 3개 | 미연결 (CH6~8에 배선) |
| 0x40 CH0~3 | — | FR 3개 + RR-Lower | 미연결 |
| 0x40 CH4 | rr-shoulder | RR-Upper | ⚠️ 뒤바뀜 |
| 0x40 CH5 | rr-upper | RR-Shoulder | ⚠️ 뒤바뀜 |

**결론**: `_channel_map`(work09.md §4의 좌/우 분리)은 옳고, FL 다리가 그 규칙대로 배선되어 있었다. 소프트웨어 remap이 아니라 **배선을 코드 기준에 맞추는 방향**으로 재작업하기로 결정. 7채널이 어차피 비어 있어 물리 교체 부담이 작기 때문이다.

### 6.3 배선 기준표

```
     로봇 앞쪽 ↑                          로봇 앞쪽 ↑
0x41 (배터리 좌측) — 왼쪽 다리        0x40 (배터리 우측, 반전 장착) — 오른쪽 다리
  CH0   FL-Lower                        CH13  FR-Lower
  CH1   FL-Upper                        CH14  FR-Upper
  CH2   FL-Shoulder                     CH15  FR-Shoulder
  CH13  RL-Lower                        CH0   RR-Lower
  CH14  RL-Upper                        CH1   RR-Upper
  CH15  RL-Shoulder                     CH2   RR-Shoulder
  CH3~CH12  비워둠                       CH3~CH12  비워둠
   ↑ CH0 이 앞쪽                          ↑ CH15 가 앞쪽
```

규칙 세 가지:
1. 각 보드는 **자기 쪽 다리 2개**만 담당 (좌측 = FL+RL, 우측 = FR+RR)
2. 다리 하나는 **Lower → Upper → Shoulder** 순
3. **각 다리에 물리적으로 가까운 헤더**를 쓴다. 보드 장착 방향에 따라 어느 블록이 앞다리인지 달라진다

커넥터 방향은 work09.md §7 기준 **PWM(노랑) / V+(빨강) / GND(갈색)**.

### 6.4 CH3~5 → CH13~15 변경, 그리고 우측 보드 반전

최초 계획은 각 보드에서 앞다리 CH0~2, 뒷다리 CH3~5를 쓰는 것이었으나 **실제 배선 시 뒷다리까지 선 길이가 부족**했다. 뒷다리는 보드에서 물리적으로 멀기 때문이다. PCA9685의 16개 채널은 전기적으로 완전히 동일하므로, 보드 끝단(CH13~15)을 써서 배선 여유를 확보했다.

추가로 **우측 PCA9685(0x40)는 좌측과 반대 방향으로 장착**되어 있음을 확인했다. 즉 이 보드는 CH15 쪽이 로봇 앞을 향한다. 따라서 우측 보드만 블록 배정을 뒤집어 **앞다리(FR)에 CH13~15, 뒷다리(RR)에 CH0~2**를 할당했다.

> 배선을 코드에 억지로 맞추지 않고, **배선이 짧아지는 쪽으로 꽂은 뒤 `_channel_map`을 거기에 맞추는** 방식을 택했다. 채널 간 전기적 차이가 없으므로 이쪽이 합리적이다.

## 6.6 오프셋 캘리브레이션 (완료)

`servo_check.py cal` 로 12개 관절을 기준 자세에 맞춰 실측했다.

**기준 자세 = IK 의 `theta=0`**: 어깨관절부터 발끝까지 하나의 수직 직선.

| 관절 | 측정 기준 | 목표 | 눈으로 확인 |
|------|-----------|:----:|-------------|
| Shoulder | 정면도에서 다리 축과 수직선 사이 | 0° | 발끝이 어깨관절 바로 아래 |
| Upper | 측면도에서 대퇴부와 수평면 사이 | 90° | 무릎관절이 엉덩관절 바로 아래 |
| Lower | 대퇴부-하퇴부 내각 | 180° | 발끝이 무릎관절 바로 아래 |

> 이것은 **직립 자세가 아니다.** 실제로 서 있을 때는 IK 가 무릎을 굽힌다 (work06.md §4). 여기서는 각도 0 의 기준점만 잡는다.

### 실측 결과

```python
# 기존 (Jetson 시절 다른 개체)
self._servo_offsets = [170, 85, 90, 1, 95,  90, 172, 90, 90, 1, 90, 95]
# CM4 이식 후 실측
self._servo_offsets = [150, 81, 79, 1, 95, 105, 164, 81, 82, 1, 80, 81]
```

| idx | 관절 | 기존 → 실측 | idx | 관절 | 기존 → 실측 |
|:---:|------|:-----------:|:---:|------|:-----------:|
| 0 | FL-Lower | 170 → **150** | 6 | RL-Lower | 172 → **164** |
| 1 | FL-Upper | 85 → **81** | 7 | RL-Upper | 90 → **81** |
| 2 | FL-Shoulder | 90 → **79** | 8 | RL-Shoulder | 90 → **82** |
| 3 | FR-Lower | 1 → 1 | 9 | RR-Lower | 1 → 1 |
| 4 | FR-Upper | 95 → 95 | 10 | RR-Upper | 90 → **80** |
| 5 | FR-Shoulder | 90 → **105** | 11 | RR-Shoulder | 95 → **81** |

**오프셋은 좌우 대칭일 필요가 없다.** 혼(horn)이 스플라인에 물린 위치는 서보마다 다르고, 오프셋은 그 물리적 장착 상태를 담는 값이다. 해당 각도에서 관절이 기준 자세이면 그 값이 맞다.

**FR-Lower / RR-Lower 가 하한 1° 인 것은 설계상 정상**이다. `angleToServo()` 에서 우측 무릎은 `offset + theta` 로 위쪽으로만 움직인다 (좌측은 `offset - theta` 로 아래쪽). 좌우 무릎이 거울 대칭 장착이라 각각 가동 범위의 반대쪽 끝에서 출발한다.

## 6.7 `servoRotate()` 이중 보정 버그 (수정)

캘리브레이션 값을 반영하는 과정에서 발견했다. `servoRotate()` 에 아래 변환이 살아있었다.

```python
self._val_list[x] = (self._val_list[x] - 26.36) * (1980/1500)
```

### 정체

ServoKit 기본 펄스 범위(750~2250µs, 폭 1500)를 실제 서보 범위(460~2440µs, 폭 1980)로 맞추던 보정이다. 역산하면 정확히 일치한다.

```
θ_cmd = -290×180/1500 + θ×(1980/1500) = 1.32θ - 34.8
코드:  (θ - 26.36)×1.32               = 1.32θ - 34.8
```

### 문제

현재 코드는 이미 `set_pulse_width_range(500, 2500)` 으로 범위를 명시하므로 **보정이 이중으로 걸린다.** 그 결과 오프셋 자체가 범위를 벗어난다.

```
FL-Lower offset 170 → (170-26.36)×1.32 = 189.6 → "Over 180!!"  → 179 클램프
FR-Lower offset   1 → (1-26.36)×1.32   = -33.5 → "Under 0!!"   → 1 클램프
```

**자기 기준값조차 재현하지 못하는 상태**였다. `servo_controller_modify.py:102` 와 `modify2.py:114` 에서 같은 줄이 주석 처리되어 있고, `servo_controller_fix.py` 는 `min_pulse=460, max_pulse=2440` 을 직접 지정하는 방식으로 대체한 것도 같은 판단으로 보인다.

→ **변환식 제거.** 이제 캘리브레이션한 raw 각도가 그대로 서보에 전달된다.

### 남은 이슈 — 클램프 시 서보 미구동

```python
if (self._val_list[x] > 180):
    self._val_list[x] = 179
    continue          # 클램프 값을 계산해놓고 서보에 쓰지 않는다
```

`continue` 가 서보 명령을 건너뛰므로, 범위를 벗어난 관절은 179 로 제한되는 것이 아니라 **이전 위치에 멈춘다.** 보행 중이면 다리 하나만 얼어붙는다. 변환식 제거 후에는 클램프가 발동할 일이 거의 없어 일단 현행 유지하고, 실제 보행에서 `Over 180!!` 로그가 나오는지 보고 판단한다.

## 6.8 직립 자세 목표값 조정

캘리브레이션 후 `servo_controller.py` 를 실행하니 **RR-Upper 가 `Under 0!!` 로 걸려 명령이 전송되지 않았다.**

### 원인 — 앞뒤 비대칭은 코드 버그가 아니다

`__main__` 의 기존 목표값은 `x=±100`, 즉 앞발을 엉덩관절보다 30mm 앞, 뒷발을 30mm 뒤로 뻗는 자세다. 몸통(L=140, 관절 x=±70)과 목표값 모두 앞뒤 대칭인데 IK 결과는 대칭이 아니다.

|-----------|:------------:|:------------:|

기존 오프셋(RL/RR Upper = 90)으로 계산해도 `90−(−85)=175`, `90+(−85)=5` 로 아슬아슬했다. 이번 캘리브레이션에서 80~81 로 낮아지며 −5 로 넘어갔을 뿐, **`__main__` 의 기본 목표값 자체가 무리한 자세**였다.

### 조정 결과

발끝을 엉덩관절 바로 아래로 옮기고 몸통 높이를 120mm 로 올렸다.

## 6.9 Upper 관절 조립 방향 검증

뒷다리 Upper 조립이 의심되어 확인했다. **오프셋 캘리브레이션만으로는 서보가 뒤집혀 장착된 경우를 잡을 수 없다** — 뒤집혀 있어도 "수직이 되는 각도"는 정상적으로 찾아내지만, theta 가 변할 때 반대 방향으로 움직인다.

**검증 절차**

1. 네 Upper 를 각자의 오프셋으로 (1→81, 4→95, 7→81, 10→80) → 모두 수직 하방인지 확인
2. 네 Upper 에 동일한 theta(+20°) 적용 (1→61, 4→115, 7→61, 10→100) → 모두 같은 방향으로 기우는지 확인

`angleToServo()` 는 좌측을 `offset − theta`, 우측을 `offset + theta` 로 다루므로(거울 대칭 장착 전제), 같은 theta 에 대해 서보 값은 좌우가 반대로 움직이지만 **허벅지는 같은 방향으로 기울어야** 한다.

→ 두 단계 모두 정상 확인. 뒤집힌 서보 없음. FR-Upper 오프셋이 95 로 나머지(80~81)와 15° 차이나는 것도 혼 장착 위치 차이일 뿐 정상이다.

> 처음 촬영한 사진에서 좌우 뒷다리가 크게 달라 보였던 것은 조립 문제가 아니라, **RR-Upper 가 `Under 0!!` 로 명령을 받지 못해 혼자 이전 자세에 멈춰 있었기** 때문이다. 자세를 비교할 때는 반드시 네 관절을 동일 조건으로 맞춘 뒤 볼 것.

## 6.10 보행 궤적 사전 검증 (실물 구동 없이)

§6.8 에서 드러난 "뒤로 뻗을 때 각도가 급격히 커지는" 특성은 보행에도 영향을 준다. 보행 중 서보가 범위를 벗어나면 `servoRotate()` 가 그 관절 명령을 건너뛰어 **다리 하나가 얼어붙는다** (§6.7). 땅에 서 있는 상태라면 넘어진다.

```
TrottingGait.positions(t, kb_offset)   발끝 궤적 4개
```

`pos=(50, 80, 0)` 는 `start_automatic_gait.py` 의 `bodyX=50`, `40+height(40)=80` 에서 온다.

### 결과 — 전 구간 범위 내

키보드 한 번 누를 때 `Sl±10`, `Sw±5`, `Sa±3` 씩 누적된다 ([Common/multiprocess_kb.py](../../Common/multiprocess_kb.py) 의 `X_STEP`/`Y_STEP`/`YAW_STEP`).

| 입력 | 서보 min~max | 여유 |
|------|--------------|:----:|
| 정지 | 12.6 ~ 148.4 | 13° |
| 전진 3회 (Sl=30) | 12.3 ~ 148.7 | 12° |

| 정지 자세 `feetPosition(Lp)` | 32.8 ~ 128.2 | 33° |

**보폭을 키워도 여유가 거의 변하지 않는다.** 자세를 결정하는 것은 보폭이 아니라 기본 발 위치(앞 `Fo=120`, 뒤 `Ro=-50`)와 몸통 오프셋 `(50, 80)` 이기 때문이다.

**한계 관절은 `RR-Upper` (12.4 ~ 35.2)** — §6.8 에서 `Under 0!!` 로 걸렸던 그 관절이다. 보행 중 경고가 뜨면 여기부터 확인할 것.

### 부수 발견 — `calcLeg()` 0 나누기

```python
# Kinematics/kinematicMotion.py
tp = 1/(self.t1/td)     # td == 0 이면 ZeroDivisionError
```

`t` 가 정확히 `t0`(300ms)일 때 `td=0` 이 되어 보행 프로세스가 죽는다. 실수 시간이라 확률은 낮지만 수식을 정리하면 애초에 발생하지 않는다.

```python
tp = td/self.t1         # 수학적으로 동일, td=0 에서 0
```

`t3` 구간(발 들어올리기)에도 같은 패턴이 있어 함께 수정했다.

## 6.11 보행 테스트 — SSH 에서 키 입력이 전달되지 않는 문제

`start_automatic_gait.py` 를 실행하면 **에러 없이 돌지만 키를 눌러도 반응이 없었다.** 정지 자세만 계속 유지했다.

### 원인

`keyboard` 라이브러리의 문제가 두 겹으로 겹쳐 있었다.

1. **`import` 은 통과하지만 첫 호출에서 root 를 요구한다.**
   ```
   keyboard.is_pressed("w")
     -> ImportError: You must be root to use this library on linux.
   ```
   이 예외가 키 입력 담당 자식 프로세스를 죽이고, 메인 루프는 초기값(전부 0)만 계속 읽는다.

2. **sudo 로 실행해도 SSH 키 입력은 전달되지 않는다.** 이 라이브러리는 `/dev/input` 의 물리 키보드 장치를 직접 읽는다. SSH 의 키 입력은 pty 를 통해 오므로 도달하지 않는다. CM4 에는 물리 키보드도 연결되어 있지 않았다 (`/proc/bus/input/devices` 에 키보드 없음).

에러가 보이지 않았던 것은 **`consoleClear()` 가 매 루프마다 화면을 지우기** 때문이다.

> 이때 서보 출력값은 §6.10 의 정지 자세 예측과 거의 정확히 일치했다.
> 예측 `[74.4, 118.8, 76.6, 76.6, 57.2, 107.4, 91.1, 128.2, 84.4, 73.9, 32.8, 78.6]`
> 실측 `[75, 118, 77, 76, 58, 107, 92, 128, 84, 73, 33, ...]`
> 즉 제어 체인은 정상이었고 입력만 막혀 있었다.

### 해결 — stdin 입력 경로 추가

`Common/multiprocess_kb.py` 에 stdin 기반 입력을 넣고, `keyboardAvailable()` 로 **자동 선택**하도록 했다. 물리 키보드가 있으면 기존 방식, 없으면 stdin 을 쓴다. sudo 도 불필요해졌다.

**설계상 주의점 두 가지**

- **자식 프로세스는 stdin 을 읽을 수 없다.** `multiprocessing` 이 자식의 stdin 을 `/dev/null` 로 닫는다 (`multiprocessing.util._close_stdin`). 따라서 stdin 경로는 별도 프로세스가 아니라 **메인 루프에서 `pollStdin()` 으로 폴링**한다.
- **EOF 무한 루프.** stdin 이 닫히면 `select` 는 계속 readable 을 반환하고 `read(1)` 은 `''` 를 돌려주므로 루프가 빠져나오지 못한다. 파이프 실행이나 터미널 단절 시 CPU 를 100% 먹으며 매달린다. `ch == ''` 에서 `break` 하도록 처리.

터미널은 `tty.setcbreak()` 로 두어 Enter 없이 키를 받고, 종료 시 `termios.tcsetattr` 로 복구한다.

```
입력: stdin (이 터미널에서 w/a/s/d/q/e, space=정지, Ctrl-C 종료)
```

→ 매단 상태에서 보행 정상 동작 확인.

## 6.12 지면 보행 — 미끄러짐과 대기 구간 제거

매단 상태에서는 잘 걷는데 **지면에서는 미끄러지며 의도한 방향으로 가지 않았다.** 종이박스에서도, 카페트에서도 마찬가지였다. 발바닥이 TPU 신발 없이 PETG 노출 상태라 마찰이 불리하긴 했지만, 카페트에서도 같았으므로 원인은 따로 있었다.

### 원인 — `t0`/`t2` 대기 구간이 미끄러짐을 강제한다

```python
self.t0=300   # 시작 위치에서 정지
self.t1=1200  # 끌기 (접지)
self.t2=300   # 끝 위치에서 정지
self.t3=200   # 발 들어올리기
```

`t0`/`t2` 에서 발은 **몸통 기준 고정 위치**에 머문다. 그런데 같은 시각에 대각선 반대쪽 다리는 `t1` 에서 끌고 있다. **네 발이 모두 접지한 상태에서 두 발은 정지하고 두 발은 움직이면, 물리적으로 미끄러지는 것 외에 다른 해가 없다.**

핵심은 위치가 아니라 **속도**다. 접지한 발끼리 속도만 같으면 위치가 달라도 미끄러지지 않는다.

원저자도 알고 있었다 — 코드에 `#0 # senseless i guess`, `TODO: remove t0 and t2 - not practical` 이 남아있다.

### 정량 비교

접지 중인 발들의 x 속도 편차를 계산했다 (0 이면 미끄러짐 없음).

| 설정 (t0/t1/t2/t3) | 서보 여유 | 접지 속도 편차 |
|--------------------|:---------:|:--------------:|
| **300/1200/300/200 (기존)** | 12° | **15.5** |
| **0/1200/0/200 (채택)** | 12° | **0.0** |
| 0/1000/0/200 (원저자 주석값) | 12° | 0.6 |
| 0/1000/0/400 | 12° | 0.0 |
| 0/600/0/600 (듀티 50% trot) | 7° | 0.3 |

`t0`/`t2` 만 0 으로 두면 편차가 정확히 0 이 되고 서보 여유는 그대로다. 주기도 2000ms → 1400ms 로 짧아진다.

듀티 50% 정통 trot 은 미끄러짐엔 유리하나 두 발로만 서는 순간이 있어 **IMU 없는 개루프에서는 넘어지기 쉽고**, 서보 여유도 7° 로 준다. 채택하지 않았다.

→ 실물에서 보행이 눈에 띄게 힘차졌다. 지면을 실제로 밀기 시작했다는 뜻.

## 6.13 시계방향 회전 — FR-Upper 혼 이탈

미끄러짐이 줄자 **시계방향으로 도는 것이 뚜렷해졌다.** 정지 상태에서 발 위치를 보니 대각선 패턴이었다.

```
앞: 오른발(FR)이 더 앞    ┐
뒤: 왼발(RL)이 더 앞      ┘ 대각선 쌍 {FR, RL} 이 앞으로 치우침
```

이 쌍은 trot 에서 함께 딛는 쌍이라, 치우쳐 있으면 딛을 때마다 몸통에 회전 모멘트가 생긴다.

오프셋을 나란히 놓으면 신호가 보였다.

```
Upper:     FL 81  | FR 95  | RL 81 | RR 80    <- FR 만 14도
Shoulder:  FL 79  | FR 105 | RL 82 | RR 81    <- FR 만 25도
```

**FR 다리만 두 관절이 함께 튄다.** 확인 결과 **FR-Upper 의 서보 혼이 빠져 있었다.**

> **교훈**: 오프셋은 혼 장착 위치 차이를 흡수하는 값이라 좌우가 달라도 정상이다. 다만 **한 다리만 유독 크게 벌어지면 조립 이상을 의심할 것.** 10~15° 오차는 눈으로 "수직"을 판정할 때 놓치기 쉽다.

> **주의**: 고장난 관절을 기준으로 반대쪽을 맞추면 안 된다. 이때 FR(95) 에 맞추려고 FL-Upper 를 81 → 86 으로 올렸는데, FR 을 수리하면 FL 이 5도 틀어진 채 남는다. 81 은 "대퇴부 수직" 을 직접 본 독립 측정값이므로 되돌렸다.

### 재조립 시

서보를 먼저 90° 로 놓고 대퇴부가 수직이 되도록 혼을 결합하면 오프셋이 90 근처로 잡혀 양방향 가동 범위가 최대가 된다 (work06.md §1). 스플라인 한 칸이 약 18° 이므로, 가장 가까운 칸에 놓고 나머지 오차는 오프셋으로 흡수한다.

나머지 혼 나사도 함께 점검할 것. 하나가 빠졌다면 다른 것도 헐거울 수 있고, 보행 중 빠지면 그 다리가 통제 불능이 된다.

## 6.14 전체 재조립 후 재캘리브레이션

FR-Upper 혼 이탈을 계기로 **12개 관절 전부 재조립**하고 오프셋을 다시 측정했다.

```python
# 재조립 전
self._servo_offsets = [150, 81, 79,  1, 95, 105, 164, 81, 82, 1, 80, 81]
# 재조립 후
self._servo_offsets = [179, 88, 81, 13, 87,  88, 179, 96, 91, 5, 81, 81]
```

혼을 다시 물리면 스플라인 위치가 달라지므로 12개가 전부 바뀌는 것이 정상이다.

### 대칭성이 크게 개선됨

| 쌍 | 재조립 전 | 재조립 후 |
|----|:---------:|:---------:|
| Lower 좌 (FL/RL) | 150/164 (14) | **179/179 (0)** |
| Lower 우 (FR/RR) | 1/1 (0) | 13/5 (8) |
| Upper 우 (FR/RR) | 95/80 (**15**) | **87/81 (6)** |
| Shoulder 우 (FR/RR) | 105/81 (**24**) | **88/81 (7)** |
| Shoulder 4개 퍼짐 | 26 | **10** |

15° 이상 벌어진 쌍이 사라졌다. 범위도 안전하다 — 직립 여유 21°, 보행은 최대 보폭(Sl=80)에서도 여유 12°.

```
직립: [59, 148, 81, 133, 27, 88, 59, 156, 91, 125, 21, 81]
```

좌측 무릎 두 개가 모두 179 로 나왔는데, 실제로 그 각도에서 다리가 곧게 펴지는 것을 확인했다
(클램프에 막힌 것이 아님). 좌우 무릎이 같은 위치에 물렸다는 뜻이라 오히려 바람직하다.

### 도구 개선 — 부분 실행이 만든 혼란

`cal <인덱스>` 로 한 관절만 재고 출력된 배열을 붙여넣다가, **다른 실행에서 잰 값이 덮어써지는**
일이 반복됐다. 원인은 두 가지였다.

1. `servo_check.py` 가 `DEFAULT_OFFSETS` 를 자체적으로 들고 있어 `servo_controller.py` 와 어긋났다
   → **`servo_controller.py` 에서 직접 파싱해 읽도록** 변경. 값 중복 제거.
2. 측정하지 않은 항목도 배열에 그대로 찍혀 구분이 안 됐다
   → 항목마다 `<- 이번 측정` / `(이번에 측정 안 함 - 기존값)` 표시. 누락이 있으면 경고 출력.

## 6.16 전진 성공 — 원인은 `t3` 가 아니라 `Sh` 와 몸통 높이였다

§6.15 의 1순위 가설(`t3` 부족)은 **틀렸다.** `t3` 를 400 으로 올리자 제자리걸음은 그대로인 채
**지면에서 뒤로 주저앉기 시작**했다. 되돌린 뒤 다른 두 파라미터를 고쳐서 전진에 성공했다.

| 순서 | 변경 | 결과 |
|------|------|------|
| 1 | `t3` 200 → 400 | ❌ 뒤로 주저앉음 (네 발 지지 비율이 깎여서) |
| 2 | `t3` 400 → 200 (원복), `Sh` 40 → 20 | 주저앉음 계속 (혼 이탈 때문) |
| 3 | RL/RR-Lower 혼 재체결 | 주저앉지 않음. 그래도 전진 못 함 |
| 4 | 착지 프로파일 교체 | 착지 충격 제거 |
| 5 | **몸통 높이 80 → 100** | ✅ **전진** |

### 6.16.1 네 발 지지 비율 — `t3` 만 올리면 안 되는 이유

```
네발지지 비율 = (t1 - Tt/2) x 2 / Tt,    Tt = t1 + t3
```

| 설정 | 네 발 지지 | 두 발로만 버티는 시간 |
|------|:----------:|:---------------------:|
| `1200/200` | **71.8%** | 28% |
| `1200/400` | **50.2%** | **50%** |
| `1600/300` | 68.7% | 31% |

`t3` 를 늘리면 주기가 길어지는데 `t1` 은 그대로여서 **대각선 두 발만 딛는 구간이 두 배**가 된다.
그 구간에서는 무릎 하중도 두 배가 되어 밀리며 주저앉는다. §6.12 가 듀티 50% 트롯을
"IMU 없는 개루프에서 넘어지기 쉽다" 며 기각했는데, `t3` 만 올리면 같은 상태를 다른 경로로 만든다.

> **`t3` 를 늘릴 때는 `t1` 을 반드시 같이 늘려야 한다.**

### 6.16.2 `Sh` 가 무릎 슬루율을 지배한다 — §6.15 가설 목록에 없던 항목

스윙 `t3` 안에 발을 `Sh` 만큼 들고 보폭만큼 되돌려야 하므로, 무릎이 요구받는 각속도는 `Sh` 가 정한다.
보폭 60mm, `t1/t3 = 1200/200` 기준:

| `Sh` | 요구 슬루율 | DS3235 무부하 정격(545°/s) 대비 |
|:----:|:-----------:|:-------------------------------:|
| **40 (기존)** | **739°/s** | **136% — 초과** |
| 25 | 506°/s | 93% |
| **20 (채택)** | **427°/s** | 78% |
| 15 | 349°/s | 64% |

**`Sh=40` 은 무릎이 궤적을 따라갈 수 없는 값이었다.** 발이 다 들리기 전에 지면을 끌어
전진분이 상쇄된다 — 이것이 제자리걸음의 실제 원인 중 하나다.

> 서보가 실제로 낼 수 있는 20mm 를 명령하는 것이, 못 따라갈 40mm 를 명령하는 것보다
> **실제로 들리는 높이가 더 크다.** 능력을 넘는 궤적을 주면 결과가 나빠진다.

부수 효과로 서보 여유가 12° → 22° 로 늘었다.

### 6.16.3 착지 프로파일 — `sin(pi*tp)` 는 최악의 형태

```python
curLp[1] += self.Sh * math.sin(math.pi*tp)     # tp=1(착지)에서 하강 속도가 최대
```

`sin(pi*tp)` 의 미분은 `tp=1` 에서 최대 음수다. **발이 지면에 꽂히듯 닿는다.**

| 설정 | 수직 착지 속도 | 수평 불일치 |
|------|:--------------:|:-----------:|
| Sh=40, t3=200, Sl=110 (혼 이탈 당시) | **628mm/s** | 642mm/s |
| Sh=20, t3=200, Sl=60 | 314mm/s | 350mm/s |

정적 무릎 토크는 4~6 kg·cm 로 정격 35 의 6~9배 여유인데도 혼이 반복 이탈한 이유가 이것이다.
충격 토크는 정적 토크의 몇 배가 된다.

```python
curLp[1] += self.Sh*(1-math.cos(2*math.pi*tp))/2    # 이착지 양쪽에서 수직 속도 0
```

최고점·소요 시간·최대 속도가 모두 같고 **최대 속도가 스윙 중간으로 옮겨간다.**
부수적으로 최대 슬루 요구도 427 → 357°/s 로 내려갔다.

> **남은 문제**: 수평 불일치 350mm/s 는 그대로다. 착지하는 발은 앞으로 300mm/s,
> 접지한 발들은 뒤로 50mm/s 로 움직인다. 수평 프로파일도 착지 속도를 접지 속도에
> 맞추면(3차 Hermite) 해결되지만 최대 수평 속도가 올라가는 대가가 있다.

### 6.16.4 몸통 높이 80 → 100 — 이것이 전진을 만들었다

**증상**: 공중에서는 앞뒤 발이 같은 높이로 들리는데, **지면에서는 뒷발만 덜 들린다.**
명령은 앞뒤가 동일하므로(둘 다 `Sh=20`) 차이는 **하중에 의한 처짐**이다.

몸통을 올리면 다리가 펴져 무릎 모멘트 팔이 줄어든다. 수직 하중의 모멘트 팔은
**관절축에서 발끝까지의 수평 거리**다.

| 몸통 높이 | 앞 무릎 팔 | 뒤 무릎 팔 | 뒤 무릎 토크 | 보행 최소 여유 |
|:---------:|:----------:|:----------:|:------------:|:--------------:|
| **80 (기존)** | 61.3mm | 43.4mm | 3.04 kg·cm | 23° |
| **100 (채택)** | 45.3mm | **27.2mm** | **1.90 kg·cm** | **33°** |
| 110 | 33.6mm | 14.7mm | 1.03 kg·cm | 36° |
| 120 이상 | — | — | — | **IK 도달 불가** |

세 가지가 동시에 개선된다 — 뒤 무릎 토크 **−37%**(처짐 감소), 지면 여유 **+20mm**,
서보 여유 23° → 33°. 접지 속도 편차와 네 발 지지 비율은 변하지 않는다.

`start_automatic_gait.py` 의 `height = 40` → `60` (`bodyPosition` 에 `40+height` 가 들어간다).

## 6.17 무릎이 가장 큰 토크를 받는다 — Upper 가 아니다

직관과 반대여서 계산으로 남긴다. `Kinematic.calcLegPoints()` 로 관절 좌표를 구해 실측했다.

| 다리 | Upper 모멘트 팔 | 무릎 모멘트 팔 | 비 |
|------|:---------------:|:--------------:|:--:|
| 앞다리 (준비 자세) | **0.0mm** | **61.3mm** | Upper 는 토크가 0 |
| 뒷다리 (준비 자세) | 30.0mm | 43.4mm | 1.4배 |
| 앞다리 (보행 최대) | 30.0mm | **72.2mm** | 2.4배 |

**앞발이 엉덩관절 바로 아래**에 있어(`Fo=120` = 앞 관절 x=120) 체중이 Upper 에 모멘트를
만들지 않는다. 반면 무릎은 61mm 튀어나와 체중 전부를 받는다.

수평 추진력에 대해서는 반대다 — 모멘트 팔이 수직 거리이므로 Upper(157.9mm)가
무릎(79~90mm)보다 2배 크다. 다만 추진력은 마찰 한계상 체중보다 훨씬 작아 수직 하중이 지배한다.
그리고 **착지 충격은 거의 수직**이라 그대로 무릎에 간다.

→ 혼이 이탈한 관절이 모두 무릎(RL-Lower, RR-Lower)인 것이 이것으로 설명된다. Upper 는 멀쩡하다.
조립 시 체결에 가장 신경 써야 할 곳도 무릎이다 ([work06.md](work06.md) §1.1.1).

## 6.18 앞뒤 하중 배분 — 측정값과 기하

### 지지 다각형

`bodyX=50` 이므로 엉덩관절은 앞 `x=120`, 뒤 `x=-20` 에 온다. 발은 앞 120, 뒤 −50 이다.

```
뒷발 -50 ....... 뒤관절 -20 ....... 관절중점 50 ....... 앞관절/앞발 120
   └──────────────── 지지 다각형 170mm ────────────────┘   중심 x=35
```

**앞발은 관절 바로 아래(0mm), 뒷발은 관절보다 30mm 뒤**다. 뒷다리만 뒤로 뻗은 상태로 딛는다.

```
뒷다리 하중 = (120 - Xcom)/170 = (70 - c)/170     c = 관절 중점 기준 무게중심 편차
```

현재 `Fo=120 / Ro=50` 은 `c = -15mm` 를 가정한 값이다.

### 실측 (2026-08-17)

| 측정 | 값 |
|------|-----|
| 앞발 하중 | 800g |
| 뒷발 하중 | 1000g |
| 전체 | **2200g** |

**앞+뒤 = 1800g 인데 전체가 2200g** — 400g(18%)이 맞지 않는다. 체중계를 썼는데
1kg 대는 사람 무게용 저울의 가장 부정확한 구간이다. 어느 값을 믿느냐에 따라 결론이 갈린다.

| 신뢰하는 값 | 뒷다리 비율 | c |
|-------------|:-----------:|:-:|
| 앞 800 + 전체 2200 | 63.6% | −38mm |
| 뒤 1000 + 전체 2200 | 45.5% (앞 편중) | −7mm |

**다만 어느 쪽이든 정적 토크는 문제가 아니다.** 최악(63.6%)에도 뒷다리 하나 700g,
모멘트 팔 75mm → 약 5.3 kg·cm 로 정격 35 의 6.7배 여유다. 혼 이탈의 원인은 착지 충격이다(§6.16.3).

> **정확히 재려면**: 전체는 2.2kg 로 손저울(1kg) 범위를 넘지만 **한쪽 끝은 넘지 않는다.**
> 손저울로 앞쪽만 재고 `뒷다리 = 2200 − 앞다리` 로 구하는 것이 가장 신뢰도가 높다.
> 몸통을 수평으로 유지하는 것이 최대 오차 요인이다.

보정이 필요하면 지지 다각형 폭을 유지하며 중심만 옮긴다: `Fo = 135 + c`, `Ro = 35 - c`.
다만 뒷발을 더 뒤로 보내는 것이라 서보 여유를 5~6° 먹는다.
**배터리를 앞으로 옮기는 쪽이 대가가 없다** — 단, 이동량은
`무게중심 이동 = (물체 무게 / 전체 무게) x 이동 거리` 라서 배터리 300g / 전체 2200g 이면
100mm 옮겨도 무게중심은 14mm 만 움직인다.

## 6.19 다리별 y 트림 — 조립 오차 실시간 보정

몸통 높이를 올려 전진에 성공한 뒤, **FL 과 RR 만 바닥에 끌리는** 증상이 남았다.
이 둘은 트롯에서 함께 스윙하는 대각선 쌍이다. 부품 편차·조립 오차라 파라미터로 잡는 것이 맞다.

### 파라미터 선택 — 발끝 `y` 트림

다리별로 발끝 목표 `y` 에 보정값을 더한다. 양수 = 발끝을 몸통 쪽으로 = 다리를 짧게.

- **스윙 중**: 발이 몸통에 가까워져 지면 여유가 늘어난다 → 끌림 해소
- **접지 중**: 그 코너의 하중·자세가 바뀐다 → 기울기 보정

`Sh` 를 다리별로 주는 방법도 있지만 스윙만 건드리고 접지 자세는 못 잡는다.

### 4개 모드로 조작한다

4개 값을 직접 만지는 대신 아래 4개 모드로 조작한다. 행렬식이 −16 이므로
**이 4개가 4차원 트림 공간을 완전히 span 한다** — 어떤 조합도 이들의 합으로 만들 수 있다.

| 모드 | 키 | FL | FR | RL | RR | 의미 |
|------|:--:|:--:|:--:|:--:|:--:|------|
| 전체 | `t`/`g` | + | + | + | + | 몸통 높이 |
| 앞뒤 | `y`/`h` | + | + | − | − | pitch |
| 좌우 | `u`/`j` | + | − | + | − | roll |
| 대각 | `i`/`k` | + | − | − | + | {FL,RR} 대 {FR,RL} |
| 리셋 | `p` | | | | | |

키 1회당 1mm. 화면에 현재 트림 값이 항상 표시된다.
**끌리는 발 쪽을 + 방향으로 올린다** — FL/RR 이 끌리면 `i`.

### 한계 — 10mm

음수 트림은 다리를 더 뻗게 만들어 IK 도달 한계에 걸린다. 몸통 높이 100, 보폭 60 에서 계산:

| 크기 | 결과 |
|:----:|------|
| **10mm** | 전 모드 서보 여유 ≥20°, `legIK` 오류 0 |
| 12mm | pitch/twist 여유 12° |
| 15mm | pitch/twist **도달 불가** (`legIK` 에서 D>1) |

조립 오차 보정은 1~5mm 범위이므로 `TRIM_LIMIT = 10.0` 으로 제한했다
([Common/multiprocess_kb.py](../../Common/multiprocess_kb.py)).

## 6.20 서보 릴리즈 — 신호선이 "떠야" 풀린다

테스트하지 않을 때 서보를 풀어 stall 전류를 없애려 했으나, 소프트웨어만으로는 안 됐다.

`adafruit_motor` 의 `angle = None` → `duty_cycle = 0` → PCA9685 의 full-off 비트 `(0, 0x1000)`.
레지스터를 읽어 12채널 전부 `off=4096` 인 것을 확인했다. **그런데도 대부분 힘을 유지했다.**

### 원인 — full-off 는 신호선을 능동적으로 LOW 로 끌어내린다

`MODE2 = 0x04` 는 `OUTDRV=1`, 즉 **토템폴 출력**이다. full-off 는 핀을 LOW 로 **구동**한다.
이 로봇의 서보는 그것을 유효 입력으로 보고 마지막 목표값을 계속 유지한다.

**실측으로 확정했다** — 릴리즈 상태에서 신호선(노랑)만 헤더에서 뽑으면 그 순간 힘이 빠진다.
V+ 와 GND 는 그대로인데도 그렇다. 즉 서보는 **선이 뜬 상태(floating)** 만 신호 없음으로 본다.

> 처음에는 "JX CLS 계열은 풀리고 DSServo 계열은 유지한다" 는 모델 차이로 해석했다.
> 단품 시험에서는 릴리즈되는데 조립 상태에서는 안 되는 것이 단서였다 — 단품 시험은
> 신호선을 뽑고 하므로 floating, 조립 상태는 PCA 가 LOW 로 구동. **경계는 브랜드가
> 아니라 신호선 상태였다.**
>
> FL/FR Shoulder 만 눈에 띄게 늘어졌던 것도 릴리즈 여부가 아니라 중력 토크 차이다.
> Upper/Lower 는 다리가 회전축 바로 아래에 매달려 토크가 거의 0 이라 힘이 빠져도
> 그 자리에 있다. Shoulder 만 축에서 `l1`(50mm) 옆으로 떨어져 있어 늘어진다.
> **관절이 늘어지는지로는 릴리즈를 판정할 수 없다.** `servo_check.py status` 로
> 레지스터를 읽거나 신호선을 뽑아 비교하는 것이 확실하다.

### 해결 — OE 핀으로 고임피던스 (배선 대기 중)

PCA9685 의 `MODE2` 에서 `OUTNE=10` 으로 두면 **OE 가 HIGH 일 때 16채널 전부
고임피던스**가 된다. 신호선 12개를 동시에 뽑는 것과 같다.

```
   3.3V ──[1k]──┬── OE 핀 ──── GPIO 17
                 │
              10k(보드 내장 풀다운)
                 │
                GND
```

**풀업 방향이 핵심이다.** OE 는 액티브 로우라 LOW 가 enable 이다. 풀업을 달면:

| 상황 | OE | 서보 |
|------|:--:|------|
| 부팅 직후 / 프로그램 종료 / 크래시 | HIGH (3.0V) | **자동 릴리즈** |
| 프로그램 실행 중 (GPIO LOW) | LOW | 정상 구동 |

반대로 하면 프로그램이 끝나는 순간 OE 가 LOW 로 떨어져 서보가 다시 살아난다.
지금 상태(풀업 없음)가 그래서 영원히 enable 이다.

| 풀업 | 풀다운 | OE 전압 | 판정 (임계 2.31V) |
|:----:|:------:|:-------:|:-----------------:|
| 1k | 10k (보드 1개) | 3.00V | OK |
| 1k | 5k (보드 2개 병렬) | 2.75V | OK |
| 470Ω | 5k | 3.02V | 여유 |
| 4.7k | 10k | 2.24V | **미달** |

두 보드의 OE 는 체인 커넥터로 관통되므로 **점퍼 한 가닥이면 12개 전부** 제어된다 (도통 확인함).

### 권한 — digitalio 가 아니라 gpiod

Blinka 의 `digitalio` 는 `/dev/mem` 을 열어 root 를 요구한다. 보행 스크립트가 sudo 없이
도는 구조(§6.11)를 깨뜨리므로 문자 장치 기반 `gpiod` 를 쓴다.

```bash
sudo apt install -y python3-libgpiod
sudo usermod -aG gpio $USER      # 재로그인 필요
```

### 코드 상태

[Common/servo_oe.py](../../Common/servo_oe.py) 에 구현되어 있고
`servo_controller.py` / `servo_check.py` 에 연결되어 있다.
**배선이 없거나 gpiod 가 없으면 조용히 무시되고 기존 동작 그대로다.**

배선 후 부수 효과 하나: 페일세이프라 프로세스가 끝나면 자세가 풀리므로,
각도를 세팅하고 혼을 끼우는 `servo_check.py <idx> <angle>` 과 `home` 은
**Enter 를 누를 때까지 자세를 붙들고** 기다린다.

> **보류 중** — PCA 를 분리해 납땜해야 해서 다음으로 미뤘다. 그때까지는 테스트를
> 마치면 전원을 내리는 것이 유일한 대책이다.

## 6.21 `home` 이 무릎을 스토퍼에 밀어붙이던 문제

`home` 은 `_servo_offsets` 를 그대로 명령한다. 무릎 오프셋이 `179 / 13 / 5` 로 가동 한계에

`home force` 로 강제 가능하다. 근본 해결은 혼을 한 칸 안쪽으로 물리는 것
([work06.md](work06.md) §1.1.1).

RR-Lower 를 재체결하며 `5 → 26` 이 되어 가드 대상에서 빠졌다. 남은 것은 좌측 무릎 두 개(179)다.

## 6.22 로그에서 루프 속도를 역산한다

`start_automatic_gait.py` 는 타임스탬프를 찍지 않지만, 보행이 `Tt` 주기로 반복되므로
**한 주기가 몇 루프에 걸쳐 나오는지** 세면 Hz 가 나온다. `consoleClear()` 가 화면을 지우므로
`2>&1 | tee ~/gait.log` 로 남긴 뒤 분석한다.

```bash
grep -c IDstepLength ~/gait.log      # 루프당 정확히 1회 출력된다
```

`result_dict` 출력 1줄 + `jointAngles` 4줄 + 서보값 12줄 = 루프당 17줄이다.
서보값 시퀀스로 자기상관을 구하면 주기가 몇 루프인지 나온다.

**실측 결과**: 한 주기 1600ms 가 63 루프 → **39.4Hz (25.4ms/루프)**

| `t3` | 스윙 구간 서보 갱신 |
|:----:|:-------------------:|
| 200ms | 7.9회 |
| 400ms | 15.8회 |

루프 속도가 병목은 아니었다. `consoleClear()` 가 매 루프 셸을 fork 하지만
25.4ms 는 스윙 궤적을 표현하기에 충분하다.

> 이 방법으로 §6.11 의 예측 검증도 재확인했다. 정지 자세 실측
> `[104, 125, 79, 88, 50, 90, 107, 143, 93, 77, 34, 79]` 가 계산값과 12개 전부 일치했다.

## 6.23 SSH 반응 지연 — 로봇이 아니라 노트북 WiFi 절전

터미널이 느려지고 ping 이 6~824ms 로 불규칙하게 튀며 손실 17.6% 가 났다.
CM4 온도 65.7°C 를 의심했으나 `load average 0.13`, `throttled=0x0` 으로 무관했다.

구간을 나눠 재니 원인이 갈렸다.

| 구간 | 평균 | 최대 | 손실 |
|------|:----:|:----:|:----:|
| **CM4 → 공유기** | 12.4ms | 40ms | 6.7% |
| **노트북 → 공유기** | **85.9ms** | 277ms | **13.3%** |

SSH 는 `노트북 WiFi → AP → CM4 WiFi` 로 두 무선 구간을 거치므로 나쁜 쪽이 전체를 지배한다.
노트북(MediaTek MT7925, `mt7925e`)의 WiFi 절전이 원인이었다.

```bash
nmcli con mod <연결이름> 802-11-wireless.powersave 2    # 2 = disable
nmcli con up <연결이름>
```

결과: 공유기까지 **180ms → 3.2ms**, 최대 692 → 5.5ms, 지터 230 → 1.4ms.
연결 프로필에 저장되어 재부팅 후에도 유지된다.

CM4 쪽도 절전이 켜져 있었으나(`brcmfmac`) 5초 유휴 후에도 최대 7.5ms 로 실질적 문제는
아니었다. 변수 제거 목적으로 껐다 — 지터 1.83 → 0.42ms.

```bash
sudo apt install -y iw
sudo iw dev wlan0 set power_save off
# 영구 적용: /etc/systemd/system/wifi-powersave-off.service (enabled)
```

> **판별 기법**: ping 지연이 일정 폭으로 증가하다 뚝 떨어지는 톱니 패턴이면 절전이다.
> 상대가 주기적으로만 깨어나기 때문이다. 증가폭에서 주기를 역산할 수 있다 —
> 1초 간격 ping 에서 23ms 씩 밀렸다면 `1000 mod P = P - 23` 을 만족하는 `P ≈ 128ms`.
> 무선 절전의 깨우기 주기는 보통 100~130ms 다. 무선 간섭이면 이런 규칙적 톱니가 안 나온다.

### 6.23.1 첫 부팅에서만 WiFi 가 안 붙는 문제 — brcmfmac 로밍 크래시

전원을 넣은 첫 부팅에서는 접속이 안 되고, 재부팅하면 되는 증상이 반복됐다.
공유기 기기 목록에는 정상 연결로 보이지만 실제로는 ARP 조차 응답하지 않는다.

> 공유기 목록은 **DHCP 리스가 만료될 때까지 남는다.** 전원이 꺼져도 몇 시간은 그대로
> 보이므로 연결 상태의 근거가 못 된다. 확인은 `ip neigh` 로 ARP 를 보는 것이 확실하다.
> `INCOMPLETE` 면 같은 통신 구간에 없다는 뜻이다.

### 원인 — 로밍 처리 중 커널 크래시

```
wlan0: Association request to the driver failed      (수십 회 반복)
```

인증 실패가 아니라 **드라이버가 요청을 거부**하는 것이다. 커널 로그에 원인이 있었다.

```
Call trace:
  cfg80211_roamed          [cfg80211]
  brcmf_bss_roaming_done   [brcmfmac]    <- NULL 참조 (x0 = 0)
  brcmf_notify_roaming_status
  brcmf_fweh_event_worker
```

집이 **메시 공유기**라 AP 노드가 여러 대다 (`70:5d:cc:ad:b6:5c`, `…:5e` 등).
펌웨어가 노드 간 로밍을 시도하다 이 버그를 밟고, 한 번 죽으면 **재부팅 외에 복구가 없다.**

부팅 5회 중 2회에서 발생했다 (실패한 부팅은 association 실패 45~57회).

### 해결 — 로밍 끄기

```bash
sudo tee /etc/modprobe.d/brcmfmac.conf <<'EOF'
options brcmfmac roamoff=1
EOF
sudo update-initramfs -u
```

로봇은 고정 위치에서 쓰므로 로밍이 필요 없다. 크래시 경로 자체를 밟지 않게 된다.
적용은 모듈이 다시 로드되는 다음 부팅부터다. 확인:

```bash
cat /sys/module/brcmfmac/parameters/roamoff      # Y 또는 1
journalctl -b -k | grep brcmf_bss_roaming_done   # 아무것도 없어야 정상
```

## 6.24 튜닝 도구 — 파라미터 저장과 웹 UI

파라미터가 늘어나면서 두 가지가 병목이 됐다.

1. **재시작하면 트림이 0 으로 돌아간다.** 어렵게 찾은 값이 매번 사라진다
2. **로봇을 보면서 조작할 수 없다.** 터미널을 동시에 볼 수 없고, 촬영 중에는 더 그렇다

### 저장/복원

[Common/gait_params.py](../../Common/gait_params.py). `~/.spotmicro_gait.json` 에 저장한다.
코드가 아니라 실행 상태이므로 홈 디렉터리에 두어 rsync/git 과 무관하게 유지된다.
값이 바뀔 때마다 저장하고, 임시 파일에 쓴 뒤 `os.replace` 로 바꿔 저장 도중 전원이
끊겨도 반쯤 쓰인 파일이 남지 않는다. 깨진 파일은 기본값으로 대체한다.

대상은 **실물을 보며 맞추는 값**뿐이다 — `IDtrim`, `Sh`, `height`.
`t1`/`t3` 처럼 계산으로 검증해야 하는 값은 코드에 남긴다.

### 웹 UI

[Common/web_control.py](../../Common/web_control.py). 폰으로 `http://<로봇IP>:8080`.

제어 루프(39Hz)는 건드리지 않는다. 데몬 스레드로 `ThreadingHTTPServer` 를 띄우고
기존 `command_status` 큐를 키보드 입력과 같이 쓴다. **표준 라이브러리만** 쓰므로
로봇에 추가 패키지가 필요 없다.

> tkinter 를 검토했으나 접었다. 제어 루프가 CM4 에서 도는 이상 통신 계층은 어차피
> 만들어야 하고, 그러면 남는 차이는 "폰을 손에 들고 로봇을 보며 조작" 대 "노트북 앞에
> 앉아 조작" 뿐이다.

| 경로 | 용도 |
|------|------|
| `GET /` | 한 파일짜리 HTML (인라인 CSS/JS, 외부 리소스 없음) |
| `GET /state` | 현재 상태 JSON. 폰이 400ms 주기로 폴링 |
| `POST /cmd` | `{"leg":"RR","delta":1}` / `{"param":"height","value":65}` / `{"key":"w"}` / `{"stop":1}` |

보폭은 별도 필드가 아니라 **기존 키 카운터를 올리는** 방식으로 처리한다
(`keyCounter('w')`). `calcRbStep()` 이 매 루프 카운터에서 다시 계산하므로,
직접 값을 넣으면 덮어써진다.

### 파라미터 범위는 조합으로 결정된다

각각은 안전한데 겹치면 위험한 조합이 있다. 계산 결과:

| 조건 | 서보 여유 |
|------|:---------:|
| height 65, 트림 0 | 32° |
| height 65, 트림 ±8 | **1°** |
| height 60, 트림 ±6, 보폭 110 | **IK 도달 불가** |

**보폭이 결정적 변수**다. height 60 은 보폭 60 에서 여유 31° 인데 보폭 110 에서는
IK 가 깨진다. 정적 범위로 모든 조합을 막으면 실제 운용점(height 60)이 배제된다.

→ 범위는 현실적으로 잡고(`height 40~70`, `Sh 5~25`, 트림 ±6), **제어 루프에서
실시간 감시**한다. `servoRotate()` 가 범위를 벗어나 전송하지 못한 관절 인덱스를
반환하도록 바꿔, 그 목록과 IK NaN 여부를 화면과 웹에 경고로 띄운다.
조합을 열거할 필요 없이 실제 계산 결과로 잡힌다.

## 6.25 근본 원인 — 코드의 링크 길이가 실물과 달랐다

**이것이 §6.15 이후 모든 어긋남의 근원이었다.** `Kinematics/kinematics.py` 의 치수가
실물과 달라, IK 가 계산한 발끝 위치 자체가 틀렸다. 우리가 `height`/`Sh`/`Ro`/트림을
실물 반응으로 더듬어 맞춰온 작업의 상당 부분은 이 모델 오차를 우회하는 것이었다.

### 발견 경로

준비 자세에서 `Upper축 ~ 발바닥` 을 재니 **220mm** 가 나왔다. 그런데 코드의
`l3+l4 = 200mm` 가 그 구간의 **물리적 최대**(완전히 폈을 때)다. 굽은 자세에서
최대보다 큰 값이 나올 수는 없다. **측정이 틀린 게 아니라 모델이 틀렸다.**

### 확정된 치수

| | 코드 | 실측 | 측정 방법 |
|---|---:|---:|---|
| `l1` | 50 | **56** | 앞발 트랙폭 190mm 에서 역산 (`W + 2·l1`) |
| `l2` | 20 | **20** | 어깨축~발바닥 240 − Upper축~발바닥 220 |
| `l3` | 100 | **125** | 블렌더 측면도. STL 원피팅 122.7 과 근접 |
| `l4` | 100 | **138** | 블렌더 135 + 미끄럼방지 패드 3 |
| `L` | 140 | **185** | 앞뒤 어깨축 간격 실측. URDF(186)와 일치 |
| `W` | 75 | **78** | STL 어깨 브래킷 원피팅, 오차 0.000 |

**다리 전체 길이 200 → 263mm (1.31배), 몸통 앞뒤 140 → 185mm.**

검산: `l3+l4=263` 이면 대기 자세의 220mm 는 무릎 내각 113.5° 에 해당한다.
실측 내각 RL 115, FL 120 과 맞는다.

### 측정 방법이 중요하다 — 세 가지 함정

**1. `l3`/`l4` 는 회전축 방향 성분을 제외한다.**
두 축이 평행하므로 링크 길이는 **축에 수직인 평면에서의 거리**다. 3D 두 점 거리를
쓰면 축 방향으로 어긋난 성분까지 더해져 커진다. 블렌더를 **측면 정사영**으로 두고
재면 자동으로 맞는다.

**2. `l1`/`l2` 분해는 자세에 의존한다.**
어깨 관절이 돌면 이 오프셋 벡터가 함께 회전한다. 실제로 블렌더에서 19/26,
실물 눈대중으로 30/15 가 나왔는데 **크기는 32~33mm 로 일치**하고 분해만 달랐다.
`home` 자세(세 관절 theta=0)에서 재야 정의와 맞는다.

→ 그래서 `l1` 은 직접 재지 않고 **앞발 트랙폭에서 역산**했다.
`home` 에서 발끝 좌우 위치 = `W/2 + l1` 이므로 트랙폭 = `W + 2·l1` 이다.
IK 가 쓰는 형태 그대로여서 이쪽이 신뢰도가 높다.

**3. 어느 자세에서 쟀는지 기록할 것.**
`Upper축~발바닥` 은 `home`(곧게 편) 자세에서만 `l3+l4` 다. 대기 자세(굽힘)에서는
`√(l3² + l4² + 2·l3·l4·cos θ3)` 이라 항상 더 짧다. 이 둘을 섞어서 한동안 계산이
맞지 않았다.

### 발 위치도 함께 고쳤다

`L` 이 45mm 틀렸으니 `Fo`/`Ro` 도 전부 어긋나 있었다.

```
bodyX=50, L=185  ->  엉덩관절 앞 x=+142.5,  뒤 x=-42.5

이전 Fo=120 / Ro=50   ->  앞발이 관절보다 22.5mm 뒤, 뒷발이 7.5mm 뒤  (비대칭)
```

이 비대칭이 **전진만 안 되고 후진은 되던** 현상의 원인이었다.
(궤적 자체는 전후 대칭이다 — 전진과 후진의 관절각 범위가 완전히 같다. 확인했다.)

`Spf`/`Spr` 도 `87`/`77` 이었는데 어깨각 0 이 되는 값은 `W/2 + l1 = 95` 다.
앞뒤가 10mm 달라 **보행을 시작하는 순간 발이 옆으로 튀었다.**
정지 자세 `Lp` 도 `iXf=120`/`spurWidth=80` 을 따로 적어 궤적과 어긋나 있었으므로,
`TrottingGait` 의 `Fo`/`Ro`/`Spf`/`Spr` 에서 가져오도록 바꿨다.

### 트롯의 균형 조건 — 무게중심은 대각선 위에 있어야 한다

주기의 28.6% 를 대각선 두 발로만 버틴다. 그때 지지면은 면이 아니라 **선**이다.
그 선이 중심선을 지나는 x 에 무게중심이 있어야 넘어지지 않는다.

```
발이 관절 바로 아래(Fo=142.5, Ro=42.5)  ->  대각선 교차 x = 50
실측 무게중심 (앞 800g / 전체 2200g)    ->  Xcom = 24.8
                                            25mm 어긋남
```

`pitch` 트림은 최대(10mm)로도 무게중심을 **16mm** 밖에 못 옮긴다
(기울기 6.2°, 무게중심 높이 150mm 기준). 그래서 한계에 붙여도 부족했다.

→ **발을 앞뒤 모두 25mm 뒤로** 옮겨 지지 다각형을 무게중심에 맞췄다.

```
Fo = 117.5,  Ro = 67.5     대각선 교차 x = 25.0  (무게중심 24.8)
                           발이 관절 대비 앞 -25, 뒤 -25  (대칭 유지)
                           무릎 최대 모멘트 팔 79.1 -> 68.7mm (13% 감소)
```

> 배터리·보드를 앞으로 옮겨 무게중심을 25mm 전진시키면 `142.5/42.5` 로 되돌리는
> 편이 더 좋다. 다리가 수직일 때 미는 힘이 가장 크다.

### 결과

| | 구 모델 | 신 모델 |
|---|---|---|
| 서보 최소 여유 (보폭 40~80) | 12~26° | **33~46°** |
| 네 다리 무릎내각 | 앞뒤 3° 차이 | **완전 동일** |
| 어깨각 | −0.1 ~ −3.0° | **정확히 0** |
| 최대 도달거리 | 200mm | 263mm |

**보폭 −70, 트림 0 에서 지면 전진 성공.** 그전에는 앞으로 최대 숙임(트림 한계)에서만
겨우 전진했다.

### `height` 의 의미가 바뀌었다

```
어깨축~발바닥 = 140 + height,   Upper축~발 H = 120 + height

무릎내각 110도 -> height  96
        120도 ->        108
        130도 ->        118
        143도 ->        130   <- 상한. 135 에서 여유 25도, 140 부터 IK 도달 불가
```

기본값 60 → **110**, 범위 20~70 → **60~130** 으로 바꿨다.
구 모델의 60 은 새 모델에서 무릎을 86°까지 접는 극단적 자세였다.

```bash
$P JetsonNano/examples/servo_check.py status     # 채널별 구동 여부 (레지스터 읽기, 서보 안 움직임)
```

**캘리브레이션 순서는 다리마다 Shoulder → Upper → Lower** 다 (`CAL_ORDER`).
Shoulder 가 안 맞으면 다리가 옆으로 벌어진 상태이고, 그 상태로 측면에서 "대퇴부 수직" 을
판정하면 왜곡되기 때문이다. 결과 배열 출력은 붙여넣기 편하도록 인덱스 순서(0~11)를 유지한다.

`release` / `status` / `home` 가드는 [§6.20](#620-서보-릴리즈--신호선이-떠야-풀린다),
[§6.21](#621-home-이-무릎을-스토퍼에-밀어붙이던-문제) 참조.

레포 상대 import가 없는 독립 실행형이라 실행 위치와 무관하게 동작한다.

**안전성**: 모든 스윕은 90°에서 시작해 90°로 복귀한다. work06.md의 조립 원칙(서보를 90° 전기적 중립에서 혼 결합)에 따라 90°는 모든 관절에서 가동 범위 한가운데이므로, 무릎의 offset이 170°/1°라도 끝단에 부딪히지 않는다.
